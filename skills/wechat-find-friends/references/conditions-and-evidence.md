# 条件、证据与恢复

## 条件表

先用少量结构化记录固化用户意图，不必为简单检索建立复杂数据库。

| 条件 | 类型 | 可用证据 | 不足以确认的情况 |
|---|---|---|---|
| 备注以指定字符开头 | 必要条件或初筛条件，依用户原话 | 当前备注快照 | 只看昵称、忽略大小写分支 |
| 我发送过指定文字 | 必要条件 | 消息正文、发送人、所在会话 | 只在转发/引用内出现 |
| 对方用图片介绍自己 | 必要条件 | 图片内容＋消息归属＋相邻语境 | 群里他人名片、替同学转交的表格 |
| 年级/院系 | 用户明确确认时可作必要条件 | 本人表述、完整报名截图、精确匹配的名单行 | 从账号数字或加入年份推断 |
| 看起来未实名备注 | 通常仅用于排序 | 备注中只有表情或网名 | 把所有中文名都视为已确认身份 |

检索顺序按选择性和成本安排，不一定按用户列出的顺序执行。先做消息短语全局检索只需一次，通常比对通讯录逐人打开聊天更便宜。明确的小名单可能比消息检索更有选择性。

例如“备注以 1 或 a 开头，且我发过欢迎语，但排除已确认不参加的人”应保留为 `(prefix_1 OR prefix_a) AND outgoing_phrase AND NOT declined`。`AND` 有任一不符则不符、全部符合才符合；`OR` 有任一符合即符合、全部不符才不符；其他组合维持未知。`NOT unknown` 仍是未知，不能把未查到拒绝消息当作已同意参加。

区分三个数量：搜索可见行数、去重后的候选账号数、最终匹配数。同一个显示名可能对应不同账号，同一账号也可能在多个结果分区出现。账号未核实前保留独立候选，不凭显示名去重。主搜索中“聊天记录”“群聊”“搜索网络结果”的行只提供线索，不能直接确认好友关系。

## 单个候选的最小记录

```json
{
  "candidate_id": "本次任务内稳定标识",
  "account_ref": "本地保存的已核验账号引用",
  "original_remark": "原始文字",
  "conditions": {
    "remark_prefix": {"status": "pass", "evidence": ["e1"]},
    "outgoing_phrase": {"status": "pass", "evidence": ["e2"]},
    "image_self_introduction": {"status": "unknown", "evidence": ["e3"]}
  },
  "evidence": [
    {"id": "e1", "kind": "live_profile", "observed_at": "带时区时间"},
    {"id": "e2", "kind": "message", "sender_verified": true, "message_ref": "消息位置"},
    {"id": "e3", "kind": "image", "source_path": "本地路径", "sha256": "源文件摘要", "ownership": "unconfirmed", "readability": "thumbnail_only"}
  ],
  "decision": "unresolved",
  "remark_action": {"status": "not_requested"}
}
```

图片文件名、缓存目录和聊天列表序号分别保留，不把它们当作同一种稳定 ID。目录哈希在特定版本中可能由内部 username 计算，不能把可修改的微信号 alias 或显示名直接代入。

## 关联证据的强弱

优先使用当前账号下的消息 ID、已验证会话 ID与媒体映射，其次使用当前资料页账号与用户名单中的同类标识精确匹配。内部 `wxid`、自定义微信号、手机号是不同字段，不无条件互换。

群昵称可提供自报姓名，但需要从同一账号的群成员资料页读取。姓名相同的名单行、同分钟保存的两张图、拼音接近的微信号只提供候选线索。多项独立证据能互相印证时，写清关联过程；若归属仍不明确就维持未知。

文字可读性也独立记录：`original_readable`、`preview_readable`、`thumbnail_only`、`missing`、`unsupported`。OCR 命中后查看实际图片，尤其复核姓名中的近形字、本/硕/博、院系全称；不要把 OCR 置信度当作身份概率。

## 进度与恢复

- 记录查询条件、筛选顺序、枚举覆盖数、原始候选集和已审阅集；改变排序线索不应抹掉原始候选。
- 单人或单批完成后原子写入状态。保留失败原因，不把“尚未处理”与“没有匹配”合并。
- 恢复 UI 操作时重新确认登录账号和联系人；恢复离线索引时核对源文件指纹。
- 已确认保存的备注以账号引用追踪，不再依赖旧备注搜索。保存结果不确定时先检查现状，避免二次提交。
- 新线索先重筛已存文字；只有新条件依赖未采集的字段时才回到微信或重新 OCR。

## 从实际工作中保留的教训

1. 索引应覆盖所有结果，不能用“多次滚动没有新增”单独证明已到末尾；结合末页、总数或稳定位置判断。
2. 缓存扫描与 atime 定位同时运行会污染会话映射；两者必须分时。
3. 原图存在但容器不被通用图片库识别时，先检查格式；不能直接认定图片丢失。恢复更清晰版本后再作姓名判断。
4. 相似中文名和字母大小写都值得补查，但不能无声地替换用户指定的姓名或条件。
5. 年级、院系等高选择性信息要早问；询问期间仍可完成候选枚举、相关名单检索和离线索引。
