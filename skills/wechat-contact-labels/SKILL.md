# 微信好友分组与标签

把用户指定的已有好友加入指定标签，保留他们原有的标签。这里的“添加好友”指添加标签成员；不连带改备注、改朋友权限或发消息。

## 从来源到可核对名单

- 先利用已有上下文确定标签名、来源及范围。用户已明确要求创建和添加时，直接完成已授权部分，不再逐人重复询问。
- 多图长名单可先做本地 OCR，再回看原图核对文字。长列表跨图重叠要按连续位置合并，保留来源图片及行位置；不能只凭同名去重。朋友圈截图区分本条点赞、评论和下一条动态，不把下一条作者混入名单。
- 保留原文字、前导数字、表情和联系方式。搜索可用短姓名；精确比对可忽略空白，但不自动纠正形近字、删前缀或合并同音名。模糊字放大原图确认后再改候选文字。
- 同名结果用当前资料页、账号或用户确认的头像区分。需要询问时展示最小范围的头像对照，并继续处理无歧义的行。头像选择仅用于当次核对，不作长期账号标识。
- 源文件、OCR、真实联系人和运行记录放在仓库外的本地任务目录。公共示例使用虚构资料。

## 优先使用“添加成员”窗口

实时操作前读 [macOS 界面流程](references/macos-ui.md)。核心路径：

**通讯录 → 通讯录管理 → 创建或选中目标标签 → 右键标签 → 添加成员 → 搜索并逐个勾选 → 完成。**

普通“通讯录管理”表格中的搜索会清空之前的勾选；“添加成员”窗口可跨搜索累计选择。先用少量已确认联系人验证当前版本的行为，再继续批量处理。

1. 核验当前账号、标签全名和已有成员基线。存在同名标签或已有人数异常时先定位到唯一目标，不另外建一个同名标签。
2. 新建后回读实际标签名；看到“未命名”不代表目标已经建好。只清理本次操作意外产生且确认没有成员的空标签，不清理用户已有标签。
3. 搜索必须进入当前“添加成员”窗口的搜索框。核对搜索词和完整结果范围；短词、多结果要完成滚动枚举。首屏无命中、结果区缺失或加载中都不能记为“不是好友”。
4. 匹配唯一且来源已核实后，才把未选框改为已选。回读该行及累计人数；一次新增通常应使人数加一。已选框不要再次点；禁用或缺少 Value 的框不能单凭外观判断为已有成员。
5. 每次搜索、滚动、弹窗或保存后重新取控件；不复用旧索引、坐标或上一人的匹配结果。微信 UI 单路操作，独立 OCR、名单和记录整理可以并行。
6. 将无歧义的一批保存，剩余同名项等核清再补入。选中只记为 `selected`，点“完成”后记为 `submitted_unconfirmed`；只有当前标签中的成员关系核实后才记为 `verified_member`。

## 保存、恢复与验收

- 微信可能逐人更新标签人数。保存后人数暂时偏少时观察已有提交，不立即重发整批；出现限频提示则停止 UI 批次。
- 预期人数是“原成员账号集合 ∪ 本次确认账号集合”的大小，不是简单叠加截图行数。对照已选记录、标签人数和成员身份；人数相同不能排除漏一人、多一人的抵消错误。
- 中断后重新读取目标标签，区分已保存、仅勾选和未确认的账号，只补仍缺少的成员。不要把按钮点击成功当作成员已保存，也不要自动重跑旧勾选脚本。
- 失焦、窗口变化或只读查找失败时，重新观察后做一次有依据的恢复。仍无可用证据时停下相关步骤，保留进度；不要连续猜点菜单。另一操作者占用微信时先做离线工作。
- 最后给出新增、原已存在、未解决及最终人数，记录同名判定依据。空标签清理后回到目标标签，保留可核对的最终状态。

需要离线检查精确候选、成员集合或断点记录时，读 [匹配与状态核对](references/verification.md)。附带的 `scripts/label_checks.py` 只处理 JSON，不启动微信、不点击或提交。
